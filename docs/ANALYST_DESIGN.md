# Роль «Аналитик» в Tech Lead Kit: архитектура и проверки

> Статус: **черновик на утверждение**. Кода ещё нет. После утверждения этот документ
> становится брифом для реализации (как `docs/BRIEF.md` для Tech Lead Kit).

---

## 1. Бриф: принятые решения

| Вопрос | Решение |
|---|---|
| Что строим | Роль **аналитика** внутри Tech Lead Kit: анализ данных и кода, поиск улучшений, оценка идей и кода **в цифрах** |
| Режимы работы | 1) найти возможности; 2) оценить идею или код (насколько улучшит); 3) проверить, что код отвечает задаче; 4) ответить на вопрос по данным |
| Универсальность | Работает по **темам** (topic). Каждая тема описывается профилем; чеки — первая тема, не единственная |
| Встраивание | **Вариант 4**: часть Tech Lead Kit, тот же `install.cmd`, префикс `tl-an-` |
| Источник данных первой темы | SQL MCP **`meet-chequemis`** |
| Эталон (ground truth) | Решение **פקיד** (ручная проверка чека) — оно есть в истории |
| Допустимая ошибка | **до 2%** (точное определение в §6.2, подтвердить) |
| Вычисления | Только SQL (в базе) и Python **стандартной библиотеки**. pandas не нужен. Claude «в уме» числа не считает |
| Доступ к данным | Видеть можно всё (облако компании). В отчёты идут агрегаты и короткие примеры |
| Язык | Общение **и отчёты аналитика — на русском** (исключение из правила «документы на иврите») |
| Автономность | Полуавтомат: сам ищет ответы в коде и базе; вопрос задаёт только если ответ меняет вывод (§5.8) |
| Ограничения | Без плагинов, без hooks, без интернета, перенос через USB — как у всего kit |

## 2. Как это выглядит в работе

```
Ты:      /tl-an Хочу поднять автоматическое разрешение чеков выше 8%

Аналитик: Темы «чеки» ещё нет → создаю профиль темы.
          • нашёл таблицы в meet-chequemis, поле решения פקיד, поля OCR
          • нашёл в коде текущие правила авто-разрешения (7 условий, файл:строка)
          ❓ 2 вопроса (у каждого есть ответ по умолчанию) → ты подтверждаешь профиль
          • baseline: за 6 месяцев авто-разрешено 8,1% ✔ совпадает с известными 8%
          • 92% ушли к פקיד, из них 71% разрешены без изменений → это «потолок» возможностей
          • 5 гипотез; 2 прошли проверку, 1 провалилась, 2 — мало данных
          → отчёт: правила H-002 + H-004 вместе: 8% → 13,4%, ошибка 0,9% (верхняя граница 1,4%)
```

```
Ты:      /tl-an-verify docs/task-512.md src/ChequeRules/

Аналитик: Матрица «требование → код»: 6 из 7 требований выполнены, 1 нет (файл:строка).
          Эффект кода на истории: 8% → 11,2%, ошибка 1,3% (верхняя граница 1,8%) → PASS.
```

## 3. Архитектура: что добавляется в kit

`+` новое, `~` изменяется.

```
kit/.claude/
├── tech-lead-kit/CORE.md        ~ +≈20 строк: класс задачи ANALYSIS, язык отчётов,
│                                   режим аналитического чтения MCP, ссылки на новое
├── skills/
│   └── tl-analytics/            + новый skill
│       ├── SKILL.md               цикл анализа, правило доказательности, выбор сценария
│       ├── references/
│       │   ├── topic-profile.md                  шаблон профиля темы
│       │   ├── playbook-decision-automation.md   правила авто-решения против решения человека (чеки)
│       │   ├── playbook-metric-drivers.md        почему метрика такая / почему изменилась
│       │   ├── playbook-change-impact.md         эффект изменения: до/после, what-if
│       │   ├── playbook-requirement-trace.md     код против задачи
│       │   ├── backtest-sql.md                   шаблоны SQL бэктеста: SQL Server + DB2 z/OS
│       │   ├── statistics.md                     интервалы, размер выборки, ловушки
│       │   ├── analytical-read-safety.md         как читать большие таблицы PROD безопасно
│       │   └── report-template.md                шаблон отчёта
│       └── scripts/
│           └── an_stats.py        Python, только stdlib: интервалы, минимальная выборка,
│                                  сравнение долей, стабильность по периодам, --selftest
├── commands/
│   ├── tl-an.md               + единая точка входа: понимает задачу и запускает нужный поток
│   ├── tl-an-topic.md         + создать / обновить тему
│   ├── tl-an-baseline.md      + измерить текущее состояние
│   ├── tl-an-explore.md       + найти возможности → гипотезы
│   ├── tl-an-eval.md          + оценить идею / гипотезу / код: бэктест + вердикт
│   ├── tl-an-verify.md        + код против задачи (+ оценка эффекта)
│   └── tl-an-report.md        + итоговый отчёт по теме
└── agents/
    ├── tl-an-code-tracer.md   + извлекает РЕАЛЬНУЮ логику решений из кода (таблица решений)
    ├── tl-an-data-profiler.md + находит и профилирует данные темы (только чтение)
    └── tl-an-skeptic.md       + независимый критик: ищет дыры, пересчитывает ключевые числа
```

**Почему префикс `tl-an-`:** `install.cmd` и `uninstall.cmd` уже прячут от git и удаляют всё
по маске `tl-*`. Новые файлы попадают под те же маски — скрипты почти не меняются. А набрав
`/tl-an`, ты видишь в подсказке все команды аналитика вместе.

**Почему именно эти 3 агента:**

| Агент | Зачем отдельно | Инструменты |
|---|---|---|
| `tl-an-code-tracer` | Чтение большого кода не засоряет главный контекст; результат — компактная таблица решений | Только `Read`, `Grep`, `Glob` |
| `tl-an-data-profiler` | Каталог и профили таблиц — много вывода; наружу идёт только карта данных | Чтение + SQL MCP (только SELECT) |
| `tl-an-skeptic` | Автор вывода не может сам себя честно проверить; критик независим и пересчитывает числа | Чтение + SQL MCP (только SELECT) + `an_stats.py` |

Существующие `tl-architect-reviewer` и `tl-sql-reviewer` не меняются.

### Память проекта

```
.claude/tl-memory/
├── PROJECT_CONTEXT.md            (есть) аналитик берёт оттуда карту баз и стек
└── analysis/                     + новое
    ├── INDEX.md                  список тем: статус, KPI сейчас, последний отчёт
    └── <тема>/                   например cheques-auto-approval/
        ├── TOPIC.md              профиль темы + допущения + открытые вопросы
        ├── DATA_MAP.md           таблицы, связи, поле-эталон, поля «известные в момент решения»
        ├── LOGIC_AS_IS.md        текущая логика из кода: таблица решений с файл:строка
        ├── BASELINE.md           метрики: дата, период, ссылка на SQL
        ├── HYPOTHESES.md         реестр H-001…: идея, прирост, риск, интервал, вердикт, статус
        ├── queries/              каждый SQL, на котором основано любое число в отчётах
        └── reports/              YYYY-MM-DD-<что>.md
```

Память лежит в `tl-memory/` → уже скрыта от git и **не удаляется** при `uninstall.cmd`.
Знания о теме накапливаются: второй запуск через месяц не изучает процесс заново.

## 4. Универсальность: «тема» + «сценарий»

Ядро аналитика ничего не знает о чеках. Всё, что специфично для задачи, лежит в **профиле темы**.
Способ анализа выбирается из **сценариев** (playbooks).

### Профиль темы (`TOPIC.md`)

| Поле | Тема 1: чеки | Пример другой темы |
|---|---|---|
| Объект анализа | Чек | Чек (поля OCR) |
| Процесс / решение | Авто-разрешение чека | Распознавание полей OCR |
| Цель (KPI) и формула | Доля авто-разрешённых ↑ (сейчас 8%) | Доля чеков, где פקיד исправлял поле ↓ |
| Эталон | Решение פקיד | Значение поля после פקיד |
| Ограничитель (guardrail) | Ошибочные авто-разрешения ≤ 2% | Время обработки не растёт |
| Источник данных | `meet-chequemis`, таблицы … | … |
| Поля «известные в момент решения» | OCR-значения, атрибуты клиента … | … |
| Период анализа | Последние N месяцев после последнего изменения процесса | … |
| Сценарий | `decision-automation` | `metric-drivers` |

### Сценарии

| Сценарий | Вопрос, на который отвечает | Главный инструмент |
|---|---|---|
| `decision-automation` | Какие условия позволят автоматически решать больше, не нарушив порог ошибки? | Бэктест правила против решения человека |
| `metric-drivers` | Почему метрика такая / почему изменилась? Где теряем? | Воронка, разложение по сегментам и периодам |
| `change-impact` | Что изменилось после релиза / что будет, если поменять X? | До/после, what-if на истории |
| `requirement-trace` | Отвечает ли код задаче? | Матрица «требование → код → статус» |

**Новый тип задачи = новый файл `playbook-*.md`.** Команды, агенты и память не меняются.

## 5. Потоки

### 5.1 `/tl-an <задача>` — единая точка входа

```
задача ─► прочитать INDEX.md ─► тема есть? ──нет──► /tl-an-topic (единственная остановка)
                                    │да
                                    ▼
                         что спрашивают?
        ┌───────────────┬───────────┴──────┬────────────────┬───────────────┐
   «как улучшить»   «оцени идею/код»  «код = задача?»   «вопрос по данным»  «итог»
        ▼               ▼                  ▼                 ▼               ▼
   baseline* →      /tl-an-eval       /tl-an-verify     SQL + ответ      /tl-an-report
   /tl-an-explore                                       с доказательством
   → /tl-an-eval (топ гипотез) → /tl-an-report
                                              * если baseline старше 30 дней или нет
```

Все отдельные команды можно вызывать и напрямую.

### 5.2 `/tl-an-topic <название> [описание]`
1. Читает `PROJECT_CONTEXT.md` (если нет — предлагает `/tl-init`, но может работать и без него).
2. `tl-an-data-profiler`: находит таблицы темы, ключи и связи, поле-эталон, объёмы по месяцам,
   индексы по полю даты, **разделяет поля на «известные в момент решения» и «появляются позже»**.
3. `tl-an-code-tracer`: находит в коде текущую логику решения → `LOGIC_AS_IS.md`.
4. Заполняет `TOPIC.md`, `DATA_MAP.md`.
5. **Остановка (единственная обязательная):** показывает профиль + ≤ 3 вопросов, у каждого
   ответ по умолчанию. Ты подтверждаешь или правишь.

### 5.3 `/tl-an-baseline [тема]`
1. KPI за период и по месяцам.
2. **Калибровка:** результат должен совпасть с известным значением (для чеков — 8%).
   Не совпал → карта данных неверна → аналитик останавливается и разбирается, а не идёт дальше.
3. Воронка: по каким причинам объект не прошёл автоматически (по условиям из `LOGIC_AS_IS`).
4. **Потолок возможностей:** среди ушедших к человеку — сколько он решил «как автоматика могла бы»
   (для чеков: разрешил без изменений).
5. Пишет `BASELINE.md` со ссылками на `queries/`.

### 5.4 `/tl-an-explore [тема] [фокус]`
1. Делит историю на **период A** (поиск) и **период B** (подтверждение, более поздний).
2. На периоде A ищет сегменты, где человек почти всегда принимает то же решение, только по полям
   «известным в момент решения»: по одному полю, затем по парам.
3. Кандидатов ранжирует по приросту KPI; каждый проверяет на периоде B.
4. Записывает гипотезы в `HYPOTHESES.md` (H-001…), лучшие передаёт в `/tl-an-eval`.

### 5.5 `/tl-an-eval <идея | H-id | путь к коду>`
1. **Формализует** в одно условие (SQL-предикат). Если дан код → `tl-an-code-tracer` строит
   таблицу решений → предикат; каждое условие сопоставлено с файл:строка.
2. **Бэктест** на периоде B: сколько объектов правило решило бы автоматически (прирост KPI)
   и сколько из них человек решил иначе (ошибка).
3. **Статистика** через `an_stats.py`: верхняя граница ошибки, стабильность по месяцам.
4. **Пересечения** с текущими правилами и с другими принятыми гипотезами: суммарный эффект
   считается по объединению условий, а не сложением.
5. `tl-an-skeptic` проверяет по чек-листу §6.3 и пересчитывает 1–2 ключевых числа своим SQL.
6. **Вердикт:** `PASS` · `PASS С УСЛОВИЯМИ` · `FAIL` · `МАЛО ДАННЫХ`. Обновляет реестр гипотез.

### 5.6 `/tl-an-verify <задача> <код>`
1. Из задачи (файл или текст) выписывает критерии: явные, неявные, граничные случаи.
2. `tl-an-code-tracer` строит реальную логику кода.
3. Матрица: критерий → где в коде → ✔ / частично / ✖ / нельзя проверить.
4. Если код меняет логику решения → запускает `/tl-an-eval` для оценки эффекта на истории.
5. Итог: «отвечает задаче: да / частично / нет» + «ожидаемый эффект: 8% → X%, ошибка Y%».

### 5.7 `/tl-an-report [тема]`
Отчёт на русском: 1 страница для руководства + детали. Рекомендуемый набор правил и суммарный
эффект, риски, план внедрения (§6.4), что мониторить после запуска.

### 5.8 Протокол вопросов (полуавтомат)
- Сначала искать ответ самому: код, база, память темы.
- Спрашивать, только если **(а)** не нашёл **и (б)** ответ меняет вывод.
- Вопросы собирать пачкой, ≤ 3 за раз, у каждого — **ответ по умолчанию** («если не ответишь,
  считаю X»). Без ответа работа продолжается с допущением, оно записывается в `TOPIC.md`.
- Каждое утверждение в отчёте помечено: **ИЗМЕРЕНО** (есть SQL) · **ОЦЕНЕНО** (расчёт с
  допущениями) · **ПРЕДПОЛОЖЕНИЕ**.

## 6. Методика (сердце аналитика)

### 6.1 Правило доказательности
- Каждое число в отчёте получено SQL или `an_stats.py` и имеет ссылку на файл в `queries/`.
- Claude не считает проценты и интервалы «в уме».
- Любой результат воспроизводим: тот же SQL на тех же датах даёт то же число.

### 6.2 Определение ошибки и проверка порога 2% (чеки, по умолчанию — подтвердить)
- **Ошибка правила** = доля чеков, которые правило разрешило бы автоматически, а פקיד
  **отклонил** *(вопрос: и/или исправил сумму / данные перед разрешением — это тоже ошибка?)*.
- Порог проверяется **по верхней границе** (95%, интервал Вильсона), а не по наблюдаемому
  значению. Иначе маленькая выборка «случайно» пройдёт.

| Наблюдение | Наблюдаемая ошибка | Верхняя граница | Вердикт |
|---|---|---|---|
| 0 ошибок на 100 чеках | 0% | 2,63% | МАЛО ДАННЫХ |
| 0 ошибок на 133 чеках | 0% | 1,99% | PASS |
| 5 ошибок на 500 чеках | 1,0% | 2,04% | МАЛО ДАННЫХ |
| 10 ошибок на 1000 чеках | 1,0% | 1,67% | PASS |
| 15 ошибок на 1000 чеках | 1,5% | 2,28% | МАЛО ДАННЫХ |
| 60 ошибок на 5000 чеках | 1,2% | 1,48% | PASS |
| 40 ошибок на 1000 чеках | 4,0% | 5,15% | FAIL |

  Правило вердикта: **PASS** — верхняя граница ≤ 2%; **FAIL** — наблюдаемая ошибка > 2%;
  **МАЛО ДАННЫХ** — наблюдаемая ≤ 2%, но верхняя граница > 2% (нужно больше истории).

- Порог действует **для каждого правила и для всех новых правил вместе**.
- Ошибку считаем **по количеству и по сумме** (₪): правило, которое ошибается редко, но на
  крупных чеках, помечается отдельно.

### 6.3 Чек-лист критика (`tl-an-skeptic` проверяет обязательно)
1. **Утечка из будущего:** правило использует только поля, известные в момент авто-решения.
   Для чеков: значения OCR, а **не** исправленные פקיד.
2. **Переобучение:** найдено на периоде A — подтверждено на периоде B.
3. **Размер выборки:** вердикт по интервалу, не по точке.
4. **Стабильность:** помесячно; ни один месяц не выбивается за порог; сезонность.
5. **Пересечения:** суммарный эффект по объединению правил.
6. **Смещение выборки:** эталон есть только у чеков, ушедших к פקיד. У текущих 8% эталона
   может не быть (если нет выборочной проверки) — это надо явно сказать.
7. **Шум эталона:** פקיד тоже ошибается; спорные случаи — выборка на ручную проверку.
8. **Стоимость ошибки:** по количеству и по сумме.
9. **Злоупотребление:** правило с порогом (например, сумма до X) — проверить, нет ли скопления
   чеков чуть ниже порога; насколько легко «подстроиться» под правило.
10. **Изменения процесса:** новая версия OCR или правил → период анализа после изменения.

### 6.4 Рекомендация по внедрению (входит в каждый отчёт)
1. **Shadow mode:** правило считается, но не действует; 2–4 недели сравнение с решениями פקיד.
2. Ограниченный запуск (часть потока / один тип чеков).
3. Мониторинг: KPI и ошибка еженедельно; **условие отката:** ошибка выше порога за неделю.

## 7. Безопасность данных: «аналитическое чтение» (изменение CORE)

Сейчас `CORE.md` разрешает на PROD только каталог и маленькие выборки, а тяжёлые запросы — только
после «да». Аналитике нужны агрегаты по истории. Предлагаемый режим:

- Только `SELECT`. Наружу возвращаются **агрегаты** (`GROUP BY`) или выборки ≤ 20 строк.
- Всегда ограниченный период **по индексированному полю даты** (индекс проверяется по каталогу).
- **Один раз на тему:** аналитик оценивает объём (сколько строк за период) и показывает план
  запросов; ты разрешаешь — дальше он работает в этом «бюджете» без вопросов на каждый запрос.
- Без блокировок PROD: SQL Server — `WITH (NOLOCK)`, DB2 — `WITH UR` (для агрегатов точность
  «до строки» не нужна).
- Никаких временных таблиц, `SELECT INTO`, процедур на PROD — только CTE и подзапросы.
- Долгий запрос → не повторять «сильнее», а разбить по месяцам.
- Если в TEST есть свежая копия истории — тяжёлое считать там.

Подробности — в `references/analytical-read-safety.md`; в `CORE.md` только короткое правило.

## 8. Python

- `an_stats.py` — **только стандартная библиотека** (`math`, `statistics`, `csv`, `json`, `argparse`).
  Работает на любом Python 3.8+, ничего ставить не нужно.
- Python к базе **не подключается**: тяжёлое считает SQL в базе, в Python идут только счётчики
  (n, ошибки, по месяцам). Драйвер БД и pandas не нужны.
- Примеры: `an_stats.py wilson --n 1000 --k 10`, `an_stats.py min-n --rate 0.02`,
  `an_stats.py stability --csv months.csv`, `an_stats.py --selftest`.
- **Этап 2 (по желанию, позже):** автоматический поиск правил деревом решений (scikit-learn) по
  выгрузке строк. Нужны пакеты через USB и драйвер БД — отдельное решение.
