# Роль «Аналитик» в Tech Lead Kit: архитектура и проверки

> Версия 2 (после обсуждения). Реализовано в kit 1.2.0 и проверено на демо (`demo/`).
> Результаты прогона: `demo/RESULTS.md`.

---

## 1. Бриф: принятые решения

| Вопрос | Решение |
|---|---|
| Что строим | Роль **аналитика** внутри Tech Lead Kit (вариант 4): анализ данных и кода, поиск улучшений, оценка идей и кода **в цифрах** |
| Режимы | 1) найти возможности; 2) оценить идею или код; 3) проверить, что код отвечает задаче; 4) ответить на вопрос по данным |
| Универсальность | Работает по **темам**; чеки — первая тема. Всё специфичное лежит в памяти темы, а не в kit |
| Откуда задача | Из разговора: твоё объяснение + документы + код + поиск по проекту и базе |
| Когда вопросы | **Только после изучения темы**, каждый с предложенным ответом. Без ответа работа продолжается с допущением |
| Эталон (чеки) | Решение פקיד (ручная проверка) |
| Допустимая ошибка | до 2%, по **верхней границе** 95% |
| Данные первой темы | SQL MCP `meet-chequemis` |
| Вычисления | Только SQL и Python **3.12+ стандартной библиотеки**. pandas не нужен. Claude «в уме» не считает |
| Доступ к данным | Видеть можно всё (облако компании). В отчёты идут агрегаты и короткие примеры |
| Язык | Общение, память темы и отчёты — **русский** |
| Ограничения | Без плагинов, hooks, интернета; перенос через USB |
| Дополнительно | Команда **`/tl-project-doc`** — документ проекта по реальному коду, базам и документам |

## 2. Что изменилось после обсуждения (v1 → v2)

| Было в v1 | Стало | Почему |
|---|---|---|
| Вопросы по теме (что считать ошибкой, порог, spot-check, движок БД) задавались мне до разработки | Аналитик выясняет это сам при изучении темы и спрашивает **после** изучения, с предложенными ответами | Твоё замечание: это вопросы темы, а не kit. Kit должен уметь их находить |
| 7 команд (`topic`, `baseline`, `explore`, `eval`, `verify`, `report`, `an`) | **2 команды**: `/tl-an-learn` и `/tl-an` | Ты даёшь задачу словами; разбивка на шаги — внутри методики, а не в командах |
| 3 агента (`code-tracer`, `data-profiler`, `skeptic`) | **2**: `tl-researcher` (фокус code / data / docs, запускается параллельно) + `tl-an-skeptic` | Один исследователь с тремя фокусами проще поддерживать; он же нужен для `/tl-project-doc` |
| 4 сценария заранее | 2 сценария (`decision-automation`, `requirement-trace`) + **общий цикл** для любой темы | Не строить заранее то, что ещё не нужно (правило 11 CORE). Новый сценарий — один файл |
| Документы только `.md` / `.pdf` | `an_doc2text.py`: `.docx` / `.xlsx` / `.pptx` → текст (stdlib) | Документы компании — Word/Excel, иврит |
| Нет памяти о ходе работы | `JOURNAL.md` темы + глоссарий в `DATA_MAP.md` | Длинный анализ продолжается в новой сессии; термины иврит ↔ колонки |
| Отчёт заканчивается рекомендацией | Отчёт заканчивается **готовой задачей для `/tl-design`** и SQL для мониторинга | Преимущество варианта 4: от анализа к реализации в одном kit |
| Стабильность: месяц выше порога = плохо | **UNSTABLE**, только если даже нижняя граница месяца выше порога; иначе **watch** | Найдено на демо: маленький месяц давал ложные тревоги |
| — | Калибровка перевода «код → SQL» на текущей логике (≥ 99% совпадения с реальными решениями) | Без неё оценка кода может быть неверной из-за ошибки перевода |

## 3. Как это выглядит в работе

```
Ты:  /tl-an-learn чеки — сейчас ~8% разрешаются автоматически, хочу больше, ошибка до 2%.
     Процесс в docs/process.docx, данные в meet-chequemis.

     → 3 исследователя параллельно (документы / код / данные)
     → профиль темы, карта данных, текущая логика с файл:строка
     → калибровка: «8%» воспроизведено по месяцам
     → вопросы с предложенными ответами («ошибкой считаю и исправление суммы, потому что…»)

Ты:  /tl-an Как поднять автоматизацию выше 8% при ошибке до 2%?
     → гипотезы → бэктест (поиск на апр–июн, подтверждение на июл–сен) → критик → отчёт

Ты:  /tl-an Проверь, отвечает ли git diff задаче docs/tasks/CHQ-512.md, и оцени эффект
     → матрица «требование → код» + эффект «как написано» vs «как требует задача»
```

## 5. Методика

**Правила аналитика** (SKILL.md): сначала изучить, потом спрашивать · каждое число из сохранённого
SQL или `an_stats.py` · метки ИЗМЕРЕНО / ОЦЕНЕНО / ПРЕДПОЛОЖЕНИЕ · проверка на истории ·
вердикт по границе · критик перед выводом · код проекта не меняется · PROD только чтение.

**Цикл:** постановка → изучение → **калибровка** (воспроизвести известное число, иначе стоп) →
базовая линия и потолок → гипотезы с механизмом → бэктест вне времени → критик → отчёт.

**Вердикт** (порог t): наблюдаемая > t → FAIL; верхняя граница ≤ t → PASS; иначе МАЛО ДАННЫХ.

| k / n | наблюдаемая | граница | вердикт |
|---|---|---|---|
| 0 / 133 | 0% | 1,99% | PASS |
| 5 / 500 | 1,0% | 2,04% | МАЛО ДАННЫХ |
| 10 / 1000 | 1,0% | 1,67% | PASS |
| 15 / 1000 | 1,5% | 2,28% | МАЛО ДАННЫХ |
| 40 / 1000 | 4,0% | 5,15% | FAIL |

**Чек-лист критика:** утечка из будущего · переобучение · размер выборки · стабильность по месяцам ·
объединение правил, а не сумма · hard stops · стоимость ошибки по сумме · подстройка под порог ·
смещение выборки и шум эталона · калибровка · безопасность запросов · доказательства в матрице.

## 6. Безопасность данных

Аналитическое чтение на PROD (`analytical-read-safety.md`): только `SELECT`, наружу агрегаты или
≤ 20 строк, период диапазоном по индексированной дате, `NOLOCK` / `WITH UR`, без временных
таблиц. **План запросов одобряется один раз на тему**, дальше работа в его рамках.

---

## 7. Документ проекта (`/tl-project-doc`)

По реальному коду, базам (каталог через MCP) и документам: назначение, архитектура, модули,
3–5 главных процессов, модель данных, интеграции, конфигурация (без секретов), сборка и тесты,
эксплуатация, безопасность, риски и техдолг, глоссарий, открытые вопросы. Каждое утверждение с
доказательством; в конце самопроверка 5 случайных утверждений. По умолчанию на иврите, по
желанию русский/английский и HTML со схемами через `oleg-skill-hesber`.

## 8. Проверки

### Автотесты — `python -m unittest discover -s tests` (34 теста, stdlib)
| Файл | Что проверяет |
|---|---|
| `tests/test_kit_structure.py` | frontmatter команд/агентов/skills, имена под масками установщика, все упомянутые файлы существуют, CORE ≤ 120 строк, команды есть в CORE и README, `install.cmd` в CRLF и **без метки внутри блока CLAUDE.md** (регрессия ошибки v1.1.0) |
| `tests/test_an_stats.py` | эталонная таблица вердиктов, крайние случаи, `min-n`, стабильность, сравнение, CLI |
| `tests/test_an_doc2text.py` | docx (иврит, заголовки, таблицы), xlsx (общие и встроенные строки, листы, лимит строк), pptx (порядок слайдов), ошибки |

### Демо — все возможности kit на учебном проекте (`demo/`)
Учебный проект ChequeFlow (Python), 36 000 синтетических чеков с заранее спрятанными
закономерностями и ловушками, docx-описание процесса на иврите, задача CHQ-512 и её реализация с
дефектами. Kit ставится в копию проекта, базы подключаются как MCP `meet-chequemis` /
`meet-checkov`, и каждая команда запускается в headless Claude Code: `/tl-init`, `/tl-design`,
`/tl-implement`, `/tl-review`, `/tl-sql`, `/tl-debt`, `/oleg-skill-hesber`, `/tl-project-doc`,
`/tl-an-learn`, `/tl-an` (улучшение), `/tl-an` (код против задачи).
Ожидаемое — `demo/EXPECTED.md`, результат — `demo/RESULTS.md`.

На рабочем компьютере после установки — короткая приёмка: `/` показывает команды, `/agents` —
4 агента, `an_stats.py --selftest` — все `ok`, `/tl-an-learn` на реальной теме воспроизводит
известное число (8%).

## 9. Ограничения и риски

| Риск | Защита |
|---|---|
| Длинные анализы съедают контекст | Исследователи в субагентах, состояние темы на диске, `JOURNAL.md` |
| Перевод логики кода в SQL неточен | Таблица решений с файл:строка, калибровка на текущей логике, сверка критиком |
| Нагрузка на PROD | Аналитическое чтение, план на тему |
| Модель «подгоняет» вывод | Правило доказательности, вердикт по границе, независимый критик |
| Демо на SQLite, а работа — SQL Server / DB2 | Шаблоны SQL написаны под SQL Server с отличиями DB2; первая реальная тема — проверить диалект |
