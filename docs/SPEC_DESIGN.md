# מנתח מערכות и знания для всех агентов — решения (kit 1.3.0)

## Зачем
Все дефекты задачи CHQ-512 в демо (правило до hard stops, нет проверки канала, `>` вместо `>=`,
нет граничных тестов) — дыры **в требовании**, а не ошибки программиста. Kit умел изучать тему
(`/tl-an-learn`), считать эффект (`/tl-an`) и проектировать (`/tl-design`). Не хватало роли
מנתח מערכות: из сырой просьбы сделать точное требование и אפיון, по которым можно писать код и
тесты без догадок.

Вторая проблема: всё, что делал kit, лежало в `.claude/tl-memory/` — локально и скрыто от git.
Новый разговор не знал про утверждённую אפיון или ADR, пока не запустишь нужную команду. Коллеги
и их агенты не видели ничего.

## Ответы владельца
| Вопрос | Ответ |
|---|---|
| Шаблон אפיון в компании | Нет. Нужна форма, которую владелец заполняет **до** начала работы → `טופס דרישה` |
| Кто пишет אפיון | Владелец или его люди → оба режима: построить и проверить |
| Формат | Markdown + красивый HTML со всеми возможностями |
| Что входит | Логика, данные, процессы, интерфейсы; экраны и отчёты — списком полей |
| Если чего-то не хватает | kit заполняет сам из того, что знает и может найти, или спрашивает |
| Знания | Проект должен «знать» результат: новую информацию видит и использует любой агент |

## Что сделано
**Skill `tl-requirements` + `/tl-spec` + критик `tl-spec-skeptic`**
- `/tl-spec new <название>` → `spec_tool.py new` создаёт `.claude/tl-memory/spec/SPEC-nnn-<slug>/REQUEST.md`.
  Обязателен только раздел 1 «что и зачем».
- `/tl-spec SPEC-nnn` → אפיון на иврите по шаблону `references/spec-template.md`: цель с числом и
  граница, что входит / не входит / **не меняется**, `REQ`, таблицы решений `DT` (порядок, hard stops
  первыми, точные границы, единицы, NULL, «אחרת», число случаев на строку), термин → `table.column`,
  кого затронет, `AC` с граничными значениями, эффект на истории (методика аналитика), внедрение,
  допущения и не больше 5 вопросов с предложенными ответами.
- Пустые поля kit заполняет из кода, данных и документов и ставит у каждого пункта
  `[מקור: …]` или `[הנחה]`.
- Перед показом: `spec_tool.py lint` (уникальные id, каждое REQ покрыто AC, AC ссылаются на
  существующие REQ, у DT есть «אחרת», нет заглушек и расплывчатых слов, у вопросов есть ответы),
  затем критик. Критик сам пересчитывает 2–3 главных числа и проверяет поля, утечки, порядок,
  противоречия и потребителей.
- `spec_tool.py render` → `SPEC.html`: один файл, офлайн, RTL, светлая и тёмная тема, печать,
  оглавление, метки REQ/AC/DT как ссылки, подсветка новых строк и «אחרת», источники и допущения
  выделены. Word открывает его и сохраняет в `.docx` (CSS-переменные Word не понимает, поэтому у
  таблиц есть `border="1"`).
- Стоп до утверждения. После «утверждаю» статус `approved`, затем `/tl-publish` и `/tl-design`
  (LARGE) или `/tl-implement` (SMALL).
- `/tl-spec check <файл>` (md / docx / pdf) → `CHECK-<дата>.md` на иврите: вердикт, находки по
  `spec-quality-checklist.md` с местом, доказательством и точным текстом исправления.
- Связь с остальными: `/tl-design` берёт требования из אפיון; `/tl-implement` превращает каждый AC
  в тест и заполняет трассировку; `/tl-review` и архитектор-ревьюер проверяют код по REQ/DT/AC;
  `/tl-an` берёт критерии из אפיון, а не из своей трактовки задачи.

**Знания для всех агентов**
- Каждый документ kit начинается со строки
  `<!-- tl-meta: type=…; id=…; status=…; date=…; area=…; title=… -->`. Строка добавлена во все шаблоны
  (אפיון, форма, ADR, дизайн, документ проекта, отчёт и тема аналитика, הסבר, реестр долга).
- `tl_knowledge.py index` собирает из этих строк `.claude/tl-memory/KNOWLEDGE.md` — карту документов:
  тип, id, статус, дата, область, где лежит. Документы без `tl-meta` перечисляются отдельно.
  CORE: в начале **каждой** задачи читать `PROJECT_CONTEXT.md` и `KNOWLEDGE.md` и открывать
  документы своей области. Утверждённая אפיון и принятый ADR обязательны: им следуют или прямо
  называют противоречие. Субагенты (исследователь, архитектор) тоже начинают с карты.
- `/tl-publish` (`tl_knowledge.py publish`) переносит утверждённые документы в `docs/` проекта.
  Перенос, а не копирование: опубликованная версия становится главной, двух расходящихся копий нет.
  Затем скрипт пишет управляемый блок «ידע על הפרויקט» в `AGENTS.md` и добавляет строку
  `@AGENTS.md` в `CLAUDE.md`. Блок содержит таблицу опубликованных документов и факты проекта из
  раздела `tl-agents` в `PROJECT_CONTEXT.md`. `AGENTS.md` читают разные агенты, Claude Code — через
  импорт.
- `/tl-publish` показывает список и ждёт «да». По умолчанию в список попадают только утверждённые
  אפיונים, ADR и дизайны; остальное — только если владелец назовёт документ.
- Перед публикацией `tl_knowledge.py check` ищет то, что нельзя отдавать команде: нет `tl-meta`,
  черновик, ссылки на локальные файлы (проверяются от **будущего** места файла), упоминания команд
  kit, `.claude/`, секреты и строки подключения. `publish` такой файл не переносит (только с `--force`
  по прямой просьбе).
- Опубликованный документ правят там, где он опубликован; локальная копия заново не создаётся.
  Если в опубликованном документе меняется статус, после `index` обновляется и блок в `AGENTS.md`.
  Номера ADR и SPEC выдаёт `tl_knowledge.py next-id`: он учитывает и локальные, и опубликованные
  документы.
- Kit **никогда не делает commit**. Опубликованный файл, который кто-то изменил, не перезаписывается
  (нужно объединить вручную). Перевод строк CRLF в `AGENTS.md`/`CLAUDE.md` сохраняется. Повторный
  запуск ничего не меняет.
- Сам kit, черновики, рабочие файлы аналитика и запросы остаются локальными. Принцип брифа «kit
  не попадает в репозиторий компании» сохранён: в проект попадают только утверждённые документы,
  и только по решению владельца.

## Что сознательно не делали
- Макеты экранов: без инструментов от них мало пользы, хватает списка полей.
- Отдельную команду для тест-сценариев: AC внутри אפיון хватает, `/tl-implement` делает из них тесты.
- Связку с Jira/ALM: нет интернета и плагинов.
- Автоматическую публикацию: файлы попадают в общий git только после «да» владельца.
- Генерацию `.docx`: Word открывает HTML и сохраняет его в `.docx`, отдельный писатель docx не нужен.

## Независимый аудит
После реализации отдельный агент проверил kit свежим взглядом и нашёл 12 существенных и 10 мелких
дыр. Блокеров не было. Все исправлены:
- одобрение плана PROD для אפיון;
- синтетические значения в AC;
- проверка ссылок от места публикации;
- «живые» документы после публикации;
- устаревший блок в `AGENTS.md`;
- обрезанное поле `area`;
- нумерация ADR;
- путь обновления с 1.2;
- подтверждение перед публикацией;
- повреждённые маркеры;
- запросы `D-n` отдельно от вопросов `Q-n`;
- мелкие недочёты.

На каждое исправление поведения есть тест.
